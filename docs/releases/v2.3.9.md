## 自动布线绑定执行 PCB

通过 `api_invoke` 调用 `eda.pcb_Document.autoRouting` 时，无参数、全网和选网任务均由 Bridge runtime 读取执行时真实 PCB，内部设置 `expectedPcbUuid`。该目标由 runtime 绑定，调用者提供的值不能覆盖实际执行身份。

handler 在原生调用前核对实际编辑器文档类型、文档 UUID 和当前 PCB UUID。显式选择最多 3 个网络时，已有布线观察读取完成后也要重新读取真实编辑器与当前 PCB；无参数或全网调用同样执行最后身份检查。最后身份 await 后紧邻同步检查连接、活动角色和租约，随后才调用原生方法，中间没有额外 await。

以下普通变化会在原生调用尚未开始时拒绝：

- 任务开始后切到另一 PCB。
- 切到原理图，但当前 PCB getter 仍保留旧页缓存。
- 最后身份读取期间连接、活动角色或租约变化。

早拒是执行前错误，零原生 autoRouting 调用；收到明确执行前拒绝时不产生 `commitUnknown` 或未知提交隔离，连接中断仍沿既有诊断恢复。本地 runtime 回归确认后续正常任务仍可执行。它不表示已经取消启动后的宿主布线任务。

## 正常参数与原有诊断

本轮保留正常原生调用的参数和 receiver，不改变自动布线算法、网络筛选或已有结果判定。指定网络仍使用官方 `RoutingNets`，例如：

```json
{
  "apiFullName": "eda.pcb_Document.autoRouting",
  "args": [{ "RoutingNets": ["NET_A"], "layers": [1], "existingPrimitiveMode": "keep" }]
}
```

无参数 `args:[]` 与 `RoutingNets:[]` 仍沿用原生全网语义。返回的原生 `result`、请求范围诊断及已有 `routingObservation` 不变；覆盖请求范围的诊断不能独立证明宿主只修改选定网络。`success:true` 仍需结合成功/总网络数、失败网络及实际图元和 DRC 判断。

已启动的原生 RPC 未确认或超时继续保留未知提交隔离，不直接重试。按诊断建立 `bridge_recover_client action:recover` 会话，重启原 EDA 宿主后，以恢复会话后的新客户端在执行时同一 PCB 完成只读 `action:readback`。使用 `readbackPath:"/bridge/jlceda/api/invoke"`、`readbackPayload:{"apiFullName":"eda.pcb_PrimitiveLine.getAll","args":[]}` 与 `hostRestartConfirmed:true`；Server 仍完整读取四类布线图元及全部网络长度，并在分段读取前后核对 PCB 身份。即时回读不是宿主调用结束的证明。

## 本轮验证范围

下列通过项来自本地 handler 或真实 runtime 配合 mock 的 fixture，不作为宿主 autoRouting 实测：

| 场景 | 核对目标 | 本轮状态 |
| --- | --- | --- |
| 无参数/全网与选网 | 执行 PCB 绑定，调用者目标不能覆盖 runtime 身份 | 定向回归通过 |
| 任务开始后换 PCB | 拒绝，零原生调用 | handler/runtime 回归通过 |
| 切到原理图而 PCB getter 有旧缓存 | 真实编辑器类型和 UUID 不匹配时拒绝 | handler/runtime 回归通过 |
| 最后身份读取期间租约变化 | 同步 guard 在原生调用前拒绝 | handler/runtime 回归通过 |
| 拒绝后的正常调用 | 下一任务可执行，原生参数原样一次调用、receiver 保持一致 | 定向回归通过 |
| 类型、lint 与独立审查 | 本轮相关文件及回归 | typecheck、相关 lint、独立源码审查通过 |
| 宿主新 guard 实测 | 匹配 2.3.9 的 EDA 实际 autoRouting | 本轮未执行 |

本轮 Bridge 完整 `npm run build`、`npm run lint` 及 Server `npm ci`、`npm test`、`npm run lint`、`node verify-multi-client.mjs` 均已通过。远端 CI/PR 审查仍按发布流程核对；上述为本轮真实本地门禁，不把既有版本门禁当成本轮新结果。
